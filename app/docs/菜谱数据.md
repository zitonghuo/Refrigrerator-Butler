## 2. 构建方式

```powershell
# 1. 取一份 HowToCook（不需要放进本仓库）
git clone --depth 1 https://github.com/Anduin2017/HowToCook.git D:\HowToCook

# 2. 生成 recipes.json
cd app
node scripts/build-recipes.cjs D:\HowToCook

# 3. 验证
npm test
npm run coverage
```

脚本输出统计（数量、分类、主料个数分布、跳过原因），并覆盖写入 `recipes.json`。

## 3. 清洗规则

HowToCook 是人工写作的 Markdown，配料写法不统一，脚本做了这些处理：

| 问题 | 处理 |
| --- | --- |
| 工具混在原料里（平底锅、烤箱、蒸笼） | 按工具词表剔除 |
| 调料变体（食用盐、白砂糖、大蒜、生抽酱油） | 归一化 + 调料规则，归入 `seasoning`，不参与匹配 |
| 括号说明（"西红柿（番茄）"） | 先整体删括号，再拆分 |
| 数量/单位（200g、3-4 根、1 汤匙） | 去掉数量，只留名称 |
| 多个写法（A/B、A、B、A 或 B） | 拆开去重，取标准名 |
| 破折号注释（"面粉—可用…"） | 删除破折号后的说明 |
| 链接/图片/URL 碎片 | 过滤 |
| 增稠剂、香精等添加剂 | 过滤 |
| 菜名是酱/汁/饮/茶/酒 | 跳过（不是菜） |
| 同义词（西红柿/番茄、土豆/马铃薯、蒜/大蒜） | `terms` 列表，匹配时都算命中 |

## 4. 抽样检查

导入前随机抽 5 道人工核对（种子固定可复现）：

| 菜名 | 分类 | 解析结果 |
| --- | --- | --- |
| 麻油拌面 | 主食 | 快熟面 + 调料，菜名与步骤真实；速食类，匹配价值一般 |
| 韩国麻药鸡蛋 | 早餐 | 鸡蛋 + 韩式酱油/味淋，味淋不常见，会落到"差一样" |
| 西红柿鸡蛋汤 | 汤 | 西红柿 + 鸡蛋，匹配良好 |
| 肉蛋盖饭 | 主食 | 米饭 + 鸡蛋 + 肉馅，匹配良好 |
| 清蒸鳜鱼 | 水产 | 鳜鱼 + 葱姜，食材具体，多数冰箱没有 |

结论：菜名、步骤真实可用；配料需要清洗，已在上表规则中处理。

## 5. 覆盖率

`npm run coverage` 用 20 组典型冰箱库存测试（番茄鸡蛋、土豆青椒猪肉、鱼葱姜……）：

```text
20 组库存
至少 1 道可做（ready）: 16 组
只差 1 样（almost）:     3 组
完全没有匹配:            1 组（羊肉 + 胡萝卜）
最优推荐平均还差:        0.2 样
```

说明：覆盖率取决于菜谱库本身，不会靠生成"补全"。羊肉、西式菜在 HowToCook 中偏少，属于已知缺口；需要时可以手工补几道真实菜谱，而不是拼菜名。

## 6. 已知限制

- 用量不换算：`servings` 只回显，菜谱里的克数保留原文，不按人数缩放
- 调味料默认为家里有：盐、油、酱油、糖、料酒、葱姜蒜等不参与匹配
- 部分菜谱偏地方/西式（印度菜、烘焙），匹配概率低，但不影响正确性
- HowToCook 更新后需要重新跑脚本并抽检，`recipes.json` 会整体覆盖
