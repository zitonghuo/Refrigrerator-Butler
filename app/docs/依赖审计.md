# 依赖审计（wx-server-sdk）

审计日期：2026-10-27
审计对象：`app/cloudfunctions/fridgeApi`、`app/cloudfunctions/fridgeMediaCleanup`
命令：

```powershell
npm audit --package-lock-only --registry=https://registry.npmjs.org --json
```

> 本机 npm 默认使用 `registry.npmmirror.com`，该镜像没有实现 audit 接口，必须显式指定官方 registry。

## 结果

6 项告警（5 high、1 moderate），全部来自 `wx-server-sdk@4.0.2` 的传递依赖：

```text
wx-server-sdk 4.0.2
├── @cloudbase/node-sdk 3.17.2
│   └── axios 0.27.2            ← 多个 SSRF / 原型污染 / 凭据泄露公告
└── @cloudbase/database 1.4.3
    ├── lodash.set 4.3.2        ← 原型污染
    └── lodash.unset 4.5.2      ← 原型污染
```

## 为什么没有直接升级

- `wx-server-sdk` 当前最新版本就是 **4.0.2**，没有已修复的新版本。
- npm 给出的 `fixAvailable` 是**降级到 2.5.3**（semver major）。本项目依赖 4.x 的 `throwOnNotFound: false`、CloudBase 事务与 `cloud.getWXContext()`，降级会破坏这些用法，不采用。
- `axios 0.27.2` 与 `lodash.set/unset` 是 `@cloudbase/*` 的**精确固定版本**（`"axios": "0.27.2"`、`"lodash.set": "4.3.2"`）。用 `overrides` 强行替换成 axios 1.x / lodash 4.x 属于跨大版本替换，可能改变 SDK 内部行为，且我们的单元测试全部 mock 了 SDK，无法覆盖真实云数据库调用，风险高于收益。

## 可利用性判断（本项目用法）

- 云函数只通过 SDK 访问固定的腾讯云数据库接口，**不接受用户提供的 URL、代理配置或请求头**，axios 的 SSRF 类问题缺少触发入口。
- 数据库读写使用常量集合名 + 服务端生成的文档 id；用户输入只作为字段值写入，不进入 `lodash.set/unset` 的属性路径，原型污染缺少入口。
- 云函数运行在微信云开发托管环境，出站网络由平台控制；项目没有自建代理。
- 结论：在当前代码用法下，这些公告**不构成可直接利用的路径**；但保留为已知风险。

## 决策

1. 保持 `wx-server-sdk@4.0.2`，不做降级、不做强制 override。
2. `release.json` 的 `cloudSdkDependencyReview` 记为已复核（`true`），并在验证备注中写明"已接受风险、上线前重新评估"。
3. 正式生产前：关注 `wx-server-sdk` / `@cloudbase/node-sdk` 新版本，升级后重跑 `npm test` 与云端联调。
4. 两个云函数使用同一 SDK，结论相同。
