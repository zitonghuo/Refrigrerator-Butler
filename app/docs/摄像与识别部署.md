# 摄像与识别：部署及验收

当前摄像功能采用免费本地预览模式（2026-10-21）：支持拍照、录像、照片放大和视频播放，不上传、不共享，退出页面后不保留预览。`mediaCloudEnabled` 与云端 `MEDIA_READY` 均未开启；包装 OCR、食材检测代码保留，服务尚未启用。重新启用云媒体前须完成存储权限、生命周期、服务部署与真机验收，并更新隐私说明及同意版本。操作见 [使用手册](小满冰箱使用手册.md)。

本次增加原生 `wx.chooseMedia` 拍照/录像/相册选择、附件查看、照片 OCR 确认入库。接口默认关闭，避免存储规则尚未配置时上传家庭影像。

## 代码状态

- 摄像入口在添加食材、食材详情、家庭页面；新页面为“照片与视频”。
- 附件归属以云函数读取的真实家庭关系为准；不信任客户端家庭 ID。
- 上传进入 staging，云函数核对文件路径、字节数、文件头后复制到 private-media。客户端不能覆盖正式文件。
- 读取先检查当前家庭成员身份，再签发 60 秒下载地址；已发出的短期链接及已下载副本不能立即撤回。
- 文件头检查用于限制格式，不等同于完整视频解码校验或内容审核。30 秒限制在客户端执行；12 MB 上限在存储规则和服务端执行。
- 本版附件保留 30 天，上传未完成文件保留 1 天；每家庭最多 100 个附件。须在上线前落实生命周期和清理任务。
- OCR 只识别包装文字。无包装食物分类、视频内容识别不在本次实现范围。

## 1. 数据库与存储

1. 新建 `fridge_media` 集合，客户端权限设为 `{"read":false,"write":false}`。
2. 云存储应用 `database/storage-rules.json`。必须确认平台支持 `resource.size` 且新文件上传能通过规则；不可通过放开所有用户读写解决兼容性问题。
3. 配置存储生命周期：`staging/` 前缀一天删除，`private-media/` 前缀 30 天删除。现有其他路径不受影响。
4. 部署 `fridgeMediaCleanup`，配置每日定时触发，事件 `Type` 为 `Timer`。确认触发上下文不包含终端用户身份，并通过一次实际运行确认可执行。该函数拒绝带微信/Web 用户标识的调用。
5. 云函数 `fridgeApi` 运行时使用 Node.js 18 或以上，建议内存至少 256 MB，超时至少 60 秒（OCR 请求超时 45 秒）。
6. 核对平台提供的 `TCB_ENV` 或 `SCF_NAMESPACE` 等于本云环境 ID；验证三步上传：申请路径、客户端上传、云函数复制确认。
7. 完成以上配置和跨账号拒绝直读验证后，再将 `fridgeApi` 的环境变量 `MEDIA_READY` 设为 `true`。不要提前开此开关。

清理任务会处理已删除、过期、家庭已解散的附件，并回收家庭附件名额。删除物理文件失败时保留记录供下次重试。任务每次最多扫描 5000 条；大规模使用前需完善游标调度、用量告警及任务监控。

## 2. 部署开源 OCR 服务

采用 https://github.com/PaddlePaddle/PaddleOCR ，Apache-2.0。使用版本 3.2.0 和 PP-OCRv5 mobile 检测/识别模型。没有复制用户提供的 Smart-Refrigerator-Management-System 源码；仅参考库存、分类、到期管理需求。

`ocr-service/` 包含 Python API、固定直接依赖版本和 Dockerfile，需要独立的 Linux 容器运行环境，例如微信云托管。它不是普通 Node 云函数，也不依赖用户电脑持续开机。

部署步骤：

1. 在有 Docker 的构建环境执行 `docker build -t xiaoman-ocr ./ocr-service`。正式部署前生成依赖锁定和镜像摘要，核查依赖安全更新；本文件的版本固定不代表已完成镜像构建验证。
2. 给容器注入随机 `OCR_TOKEN`（至少 32 字符），不可写入仓库或小程序代码。服务只接受带该令牌的请求。
3. 首次启动会下载模型，需允许官方模型源出站访问，并为运行用户的模型缓存配置持久卷。生产可在受控构建流程中预下载并校验模型。
4. 使用单进程服务，配置 HTTPS 入口、至少 2 GB 内存作为起点；用真实包装照片测量资源与时延后调整。请求体在入口限制为 4 MB，配置限流和访问权限；禁止记录请求图片与认证请求头。
5. 检查 `/health` 返回 `ready:true`，以真实中文包装 JPG/PNG 调用 `/recognize`，确认返回 `{"lines":[...]}`。
6. 在 `fridgeApi` 设置 `OCR_URL=https://实际域名/recognize` 和同一个 `OCR_TOKEN`。

图片仅通过请求进入内存，不保存到 OCR 服务磁盘；PaddleOCR 服务不训练模型。识别结果过滤低置信文本，客户端只从明确“品名”“生产日期”“保质期”“有效期至”等标签提取建议；冲突字段留空。不从生产日期自动推算到期日。用户必须勾选核对后才能带入入库表单。

没有配置 OCR 时，识别按钮明确提示服务未部署，不返回模拟识别结果。

## 2.1 可选：食材检测服务（YOLOv8）

`../../vision/` 里的识别服务可以单独部署成 HTTPS 容器，供云函数调用。它和 OCR 是两条独立通道：OCR 读包装文字，食材检测给出“画面里有什么”的候选清单。

1. 在 `vision/` 目录构建镜像：`docker build -t fridge-vision .`（默认 CPU；GPU 见 `vision/Dockerfile` 注释）。
2. 启动时设置 `FRIDGE_VISION_TOKEN`（随机长字符串），并暴露 HTTPS 入口；`GET /health` 应返回 `status: ok`。
3. 在 `fridgeApi` 云函数环境变量配置：
   - `VISION_URL=https://实际域名/recognize`
   - `VISION_TOKEN=与上面相同的令牌`
4. 客户端在“照片与视频”页对已保存照片点“识别食材”。云函数会校验附件归属、限制每分钟一次，调用服务后只返回候选清单，不写库存。
5. 候选字段：`name / quantity / unit / location / expiry / source / confidence`。数量或日期不确定时为空，用户核对后经 `item.add` 入库。

没有配置 `VISION_URL` / `VISION_TOKEN` 时，按钮明确提示“照片识别服务尚未部署”，不影响手动入库或包装 OCR。

图片会发送到外部识别服务；模型准确率有限（见 `vision/MODEL_EVALUATION.md`），结果必须人工核对，不能当作食品安全判断。

## 3. 隐私与真机验收

新版隐私版本号为 `2026-10-20-media`，需要用户重新同意；发布后台的《用户隐私保护指引》也要同步相机、麦克风、相册、媒体存储及识别用途。

- iOS、Android 分别测试拍照、录像、相册选择、取消、拒绝权限、超时与格式不支持。
- 测试 JPG/PNG、MP4；其他格式若被拒绝，应转换后重选，不要绕过检查。
- 测试超长视频、超大文件、错误文件头、上传中断以及同一页重试。
- 离开上传页面后若结果不确定，先刷新家庭附件列表核对；临时文件按生命周期清理。
- 同家庭账号能看附件；其他家庭、被移除成员不能申请链接或识别；客户端不能直接获取存储链接。
- 检查未绑定照片识别后带入表单并保存，只绑定到一个食材批次；已有食材附件识别后可生成新批次建议，但不迁移原附件。
- 测试删除附件、解散家庭、过期附件、清理任务失败重试。
- 真实 OCR 验收应覆盖模糊、反光、多个日期、竖排文字和无法识别场景。缺失日期保持空白。

## 当前验证边界

20 项 Node 自动测试通过，涵盖原有库存行为、媒体跨家庭隔离、重复确认、撤权、过期、附件归属、格式限制和日期提取；测试使用内存数据库与存储适配器，不代表云存储规则已验证。

Python 服务已做语法检查。当前电脑未检测到 Docker，未构建或运行 PaddleOCR 镜像，未测试实际图片识别。云存储规则、生命周期、清理定时器、云托管 OCR、正式隐私配置和手机摄像验收均不能据此标记完成。
