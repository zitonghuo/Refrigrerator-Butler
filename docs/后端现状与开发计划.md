## 1. 结论摘要

这个项目已经是一个**可运行的本地演示版**，不是空壳：后端是一个 281 行的 Python 标准库单文件服务，自带 8 张表、13 个接口、识别任务异步队列和本地 YOLOv8 识别服务；前端有浏览器端和微信小程序端；测试套件可直接跑通。

本轮实测：

| 项目 | 结果 |
| --- | --- |
| `python tests/test_api.py` | 10 项运行，**9 通过，1 跳过**（跳过项为视频抽帧，本机 PATH 中无 `ffmpeg`） |
| 后端依赖 | 无第三方依赖（`sqlite3` + `http.server`），Python 3.14.3 下可运行 |
| 本地识别环境 | `vision/.venv` 已装好，torch 2.11.0+cu128，**CUDA 可用（RTX 5060 Laptop）**，权重齐全 |
| 默认数据库 | `data/fridge.db` 现有 1 个家庭、1 个用户、0 条库存、1 条识别任务 |

相对实施方案，后端主线（身份/家庭、批次入库、幂等、并发、临期分档、识别任务）**已经落地**；缺口集中在方案里的**第二阶段与最后完善**：菜谱、周报、提醒待办、日期估算、纠错学习、识别置信度，以及面向部署的会话与运维能力。

## 2. 系统结构与运行时

```text
微信小程序 (miniprogram/)  ─┐
浏览器演示端 (web/)         ─┴→  server/app.py (127.0.0.1:8765)
                                     │
                                     ├→ SQLite data/fridge.db
                                     └→ 识别适配器
                                          ├ 本地服务 vision/ (127.0.0.1:8770，自动拉起)
                                          ├ 自定义 RECOGNITION_URL
                                          └ Chat Completions 兼容 VISION_URL
```

关键运行机制（读代码确认）：

- `server/app.py` 启动时调用 `ensure_local_vision()`：若未配置外部识别服务且 `vision/.venv/Scripts/python.exe` 与 `vision/weights/yolov8s.pt` 同时存在，则 `Popen` 拉起本地识别服务并轮询 `/health`（最长 90 秒），成功后把 `RECOGNITION_URL` 指向它；退出时 `atexit` 终止子进程。
- 识别是**异步任务**：`POST /api/recognize` 先插入 `tasks` 行并提交事务，再起线程调用识别；前端轮询 `GET /api/task?id=`。任务结果只是候选清单，**不直接写库存**。
- 写接口统一 `BEGIN IMMEDIATE` + `with connect()` 事务；库存变更用 `version` 乐观锁；`requests(home,key)` 实现幂等入库。
- 本地识别服务返回的候选含 `confidence / canonical_id / aliases_zh / shelf_life_days / storage_options`，但 `app.py` 的 `recognize()` 会把候选清洗为 `name/quantity/unit/location/expiry/source` 六个字段，**其余信息被丢弃**（见 4.1）。

### 3.2 方案"必须统一的业务规则"逐条核对

1. **新购与盘点分开**：✅ 新购走 `items/add`，盘点走 `items/change`；但"盘点时先与已有库存比对再让用户选择"目前完全靠前端，后端没有比对接口。
2. **同品名保留不同批次**：✅。
3. **重复画面不等于增加数量**：🟡 外部识别服务负责跨帧合并；本地服务按帧取最大计数；照片中同款多件会被算成多个候选，需人工确认。
4. **日期可追溯**：🟡 `source` 三值保留；但"保留标签信息"没有字段，估算也没有算法依据留痕。
5. **临期区间互不重叠**：✅ 5 档 + unknown，互斥。
6. **库存变化留痕**：🟡 有 `events`（操作人、数量、时间、类型）；缺纠错类型与原因，缺价格。

## 4. 缺陷与风险清单

### 4.1 P0 — 阻塞方案功能或数据正确性

1. **识别置信度被丢弃**：`recognize()` 只保留 6 个字段。方案第 1 天约定"品名、数量、单位、位置、批次、到期日、日期来源、识别置信度、任务状态"必须统一，目前缺 `confidence`，前端无法提示"低置信度待确认"。
2. **日历估算依赖的参考保质期被丢弃**：`vision/configs/fridge_metadata_v1.json` 已按品类给出 `shelf_life_days`（如水果冷藏 3–7 天、肉禽冷冻 30–90 天），本地识别也返回了 `shelf_life_days`，但后端不落库、不计算。
3. **无价格字段 → 周报金额不可得**。方案明确"缺少价格时不编造节约金额"，后端应显式返回 `amount: null` 并说明原因，而不是让前端猜。
4. **会话永不过期**：`sessions(token,user)` 无时间戳，token 明文存储；一旦泄露永久有效。本地演示可接受，但第四章"部署"和答辩演示属于必改项。
5. **`tasks` / `requests` 无清理**：识别任务含候选 JSON，长期运行会无限增长；幂等表同 key 记录永久保留。

### 4.2 P1 — 口径与健壮性

6. **临期口径与文案不一致**：分档以"到期日 23:59:59"为终点，因此 `urgent` 实际等于"今天到期"，而前端文案写的是"24 小时内"；明天上午到期的食材会落到 `soon`。建议统一为"今天到期/明天到期/3 天内/7 天内"，或改文案，二者必须写进接口文档。
7. **本地识别服务崩溃后不会重启**：`RECOGNITION_URL` 已指向死端口，后续识别只会超时失败，直到重启后端。建议在识别前做一次健康检查。
8. **识别错误信息粒度不足**：非 `ValueError` 异常统一为"识别失败，请检查服务配置或网络"，服务端只打印 traceback，前端无法区分"没配对"和"视频坏了"。
9. **前后端大小限制不一致**：前端 20 MB，后端 28 MB（`Content-Length` 上限），视觉服务同样 28 MB。
10. **未知 `GET /api/xxx` 返回 400**（`require(method=='POST')` 抛 ValueError），语义应为 404；不影响功能但接口契约不严谨。
11. **`/api/state` 无分页**：返回全部在库批次与 200 条流水，家庭数据多时会变慢（演示规模无影响）。
12. **无价格/购买日期** → 无法回答"买了几天""这批多少钱"。

### 4.3 P2 — 工程与可维护性

13. **单文件 281 行、`if` 链路由、无分层、无类型标注**：加菜谱/周报/提醒后会迅速膨胀。建议拆 `server/store.py`（连接/迁移）、`server/rules.py`（批次/临期/统计）、`server/api/`（路由），保持零第三方依赖。
14. **无数据库迁移机制**：`CREATE TABLE IF NOT EXISTS` 不能加列。新增 `price/confidence/purchase` 等列必须写"检测列 → `ALTER TABLE`"的兼容迁移。
15. **无结构化日志**：仅 `traceback.print_exc()` 与启动打印，排障靠终端。
16. **无版本信息**：建议 `GET /api/health` 返回版本、数据库可写、识别服务状态。
17. **测试缺口**：菜谱、周报、提醒、纠错、会话过期、成员移除均无用例；视频用例依赖 ffmpeg，本机跳过，视频链路实际未在本机验收。

### 4.4 环境备注（本机）

- 未安装 FFmpeg，视频抽帧链路无法在本机端到端验证；`start.bat` 也不会提示缺 FFmpeg。
- 本次分析在受限沙箱中完成：项目文件可编辑，但**外部进程写入 `data/`、`vision/.runtime/` 会被系统权限挡住**，因此服务进程与端到端识别需在普通终端或放开权限后运行；测试套件已单独放开权限跑通。

### 5.1 字段契约（对齐方案"第 1 天统一接口字段"）

| 字段 | 类型 | 出现位置 | 现状 | 建议 |
| --- | --- | --- | --- | --- |
| `name` | string ≤80 | item / candidate | ✅ | — |
| `quantity` | number >0 | item / candidate | ✅ | 候选不确定时为空串（保持） |
| `unit` | string ≤12 | item / candidate | ✅ | — |
| `location` | 冷藏/冷冻/常温 | item / candidate | ✅ | — |

| `source` | manual/label/estimate | item / candidate | ✅ | — |

### 5.2 新增 / 变更接口

| 接口 | 用途 | 关键设计 |
| --- | --- | --- |
| `GET /api/recipes?servings=2` | 菜谱 | 内置固定模板（不调 AI），按在库食材匹配度排序；排除 `expired`；返回 `matched` / `missing` / `score` / `steps`；小程序直接复用 |
| `GET /api/report/weekly?days=7` | 周报 | 从 `events` 统计入库/消耗/丢弃/盘点/纠错次数与数量（**分单位，不跨单位换算**）；`expiring_consumed` = 消耗时该批次处于临期区间；`amount` 仅当所有消耗批次都有价格时给出，否则 `null` + `reason` |
| `GET /api/todo?date=` | 每日待办 | 临期清单 + 未完成采购项 + 提醒设置；**本地没有推送通道，只提供应用内待办**，文档写明 |
| `POST /api/reminder` | 提醒设置 | `enabled` / `time` / `days_ahead`；存 `settings` 表按 home |
| `POST /api/items/change` 扩展 | 纠错 | 新增 `kind='纠错'`，`quantity` 为修正后剩余量（同盘点语义），`reason` 可选；写 `events(kind='纠错')` |
| `GET /api/alias`、自动学习 | 纠错学习 | 纠错时把"识别名 → 用户确认名"记入 `aliases`；下次入库命中别名自动替换并保留 `alias_of` |
| `GET /api/health` | 运维 | 版本、DB 可写、识别服务状态与设备 |
| `POST /api/members/remove` | 成员移除 | 需产品确认（是否允许移除他人、是否作废其会话）；README 明确未实现 |
| `POST /api/items/add` 扩展 | 价格/购买日/置信度 | 以上字段全部可选，`estimate` 且未填日期时按品类参考天数计算并标 `estimate` |

### 5.3 日期估算规则（建议）

- 仅当 `source='estimate'` 且 `expiry` 为空时计算。
- 参考天数取 `vision/configs/fridge_metadata_v1.json` 的 `shelf_life_days[location]`，取区间上限（更保守）或中位；落库 `estimate_days` 与 `estimate_basis='catalog'`。
- 计算基准是**入库当天**（或用户填写的 `purchase`），不是识别时间之后任意时刻。
- 前端必须显示"估算日期，非安全保证"（方案第 4 条要求），后端响应带 `estimate_basis` 供前端提示。
